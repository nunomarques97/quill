# Quill

Push-to-talk dictation for Windows 11, in the spirit of Wispr Flow.

Put the cursor in any window, hold a key, speak European Portuguese (with English terms mixed in) and clean, punctuated text is typed where the cursor is, without filler words or repetitions. Quill adapts to its user over time: personal vocabulary, learned corrections, writing style and the active application.

## Running Quill

Quill runs locally: Whisper through faster-whisper on the GPU, with the personal vocabulary as hints, and an optional local Ollama model for the cleanup. Audio never leaves the PC. It needs the ignored `.venv` (with `faster-whisper`) and the model files in the ignored `models/` folder; see [bench/README.md](bench/README.md) for how they were set up. Run every command from the repository folder with the `.venv` interpreter.

1. Put your own settings in `local/quill.toml` (ignored by Git), starting from [quill.example.toml](quill.example.toml): at least the `[audio] microphone` name (a prefix of the MME name; `py -3.12 -m bench.record --list-devices` lists them without opening any). Check the file with `py -3.12 -m quill.config --check local/quill.toml`.
2. Check readiness. It lists the model files, the `.venv` packages, whether the configured microphone exists (by name; it is not opened), the vocabulary, the Ollama model, the start-with-Windows entry and the learned corrections. It installs no hook, opens no window and does not open the microphone:

   ```
   .venv\Scripts\python -m quill --check
   ```

3. Start Quill. The model loads once (a few seconds; the indicator shows the loading state, and a press meanwhile records nothing):

   ```
   .venv\Scripts\python -m quill
   ```

   Ctrl+C in that console, or `.venv\Scripts\python -m quill --stop` from another one, ends it. Only one Quill runs at a time: a second start exits with code 3.

4. Optionally start Quill with Windows. These manual commands add or remove one value, `Quill`, under the current user's `Software\Microsoft\Windows\CurrentVersion\Run` key. The entry runs `.venv\Scripts\pythonw.exe` (no console window) with this folder's `quill\__main__.py`, both resolved when the command runs; run it again after moving the folder. Nothing else writes the registry.

   ```
   .venv\Scripts\python -m quill --install-startup
   .venv\Scripts\python -m quill --remove-startup
   ```

### Using it

- **Dictation** (default: hold mouse button 4, or F13, or Right Ctrl; `[triggers.dictation]`): the microphone starts at the press, so no word is lost. After `min_hold_ms` Quill clicks once at the pointer to focus the text field under it (not for Right Ctrl, which types where the focus already is). Speak; the words appear live in the indicator. On release the rest is transcribed, cleaned (fillers, repetitions, punctuation), corrected with the personal vocabulary and the learned corrections, shaped by the active window's profile and typed into the window captured at the press. It never presses Enter.
- **One session at a time**: while a released session is still being processed (transcribing, correcting, enriching, typing or pressing Enter), a press of any trigger (mouse 4, mouse 5, middle click, F13, F15, Right Ctrl, the command key, F9) starts nothing: no click, no microphone, no capture, so it never moves the focus or the caret under the text being typed. The indicator shows *Aguarde: o ditado anterior ainda está a ser escrito* for 2 s in the pending session's state, then that session's words again; the earlier session finishes with its own text and Enter. The press is logged with the reason code `previous_pending` only, and its release does nothing. The first press after the session ended works normally; a trigger still held keeps the one-hold rule. A session pending for over 120 s (a hang) no longer blocks a press.
- **Send to Claude Code**, two triggers that click to focus like a dictation, type the whole text and then press one plain Enter (no modifier), only when the text was typed completely and the target matches the `claude-code` profile:
  - **Mouse button 5 or F15** (`[triggers.send_polished]`): every dictation, whatever its length and whatever `[autorewrite]` `enabled`, `min_audio_s` and `min_words` say, first goes through the local Ollama rewrite below, with the same content guard; a refusal, an Ollama failure or a timeout types the original text with the short notice. Into Claude Code it is project-aware and enriches the prompt:
    - **Project detection** (`quill/projects.py`): the project comes from the VS Code title (the project hub format `<project> | <file> - Visual Studio Code [<view>]` gives the project, the standard `file - folder - Visual Studio Code` gives the folder) or, for Claude Code in a terminal, from a known project name in the title, else from the working folder (nearest Git root) of the single Claude Code session under that window, read read-only. The name leads to a local folder through `[project_context] folders` (only in the ignored `local/quill.toml`), then through the targets of the `[voice_commands]` shortcuts. An unknown, ambiguous or network project gives no folder: the correction then works as before, with the title hint.
    - **Context pack** (`quill/context_pack.py`, `[project_context]`): from that folder, when it is a Git work tree, a short summary of what the project is (its `CLAUDE.md`, else its `README.md`, at most 600 characters) and up to 150 of its own terms (headings and inline code of the README, `CLAUDE.md` and `docs/`, module, file and class names, words it repeats). Only files Git tracks or would track are read, so nothing the project's `.gitignore` excludes; `.env` files, keys, certificates, credential, token or secret files, audio, video, `recordings/`, `local/` and `.git/` are never read, whatever Git says, and links that leave the folder are not followed. Packs are cached under the ignored `local/context` and rebuilt when a read file or the file list changes or after `max_age_h` hours; a build slower than `build_timeout_s` gives no pack and the dictation goes on without it. Nothing leaves the PC and logs hold reason codes and counts, never project content. `py -3.12 -m quill.context_pack --check` prints the counts of each configured project.
    - **Correction with context**: the rewrite prompt carries the project name, the pack (as data, never instructions) and the personal vocabulary, and may replace a misheard word only with a project or vocabulary term that fits the context and sounds close. The content guard is unchanged: no dictated information is lost.
    - **Only terms replace words** (mouse 5 into Claude Code, with or without a known project): a fix may bring a word that was not dictated only when it is a personal-vocabulary term, one of the project's pack terms or its name; fixes of case and accents always stay. Any other fix the model makes is undone: that word is typed as it was dictated and the reply's other fixes stay. Mouse 5 in other windows and the automatic rewrite of long dictations keep their rules.
    - **Prompt enrichment** (`quill/enrich.py`): a second model call turns the corrected text into a structured prompt in the dictation's language (Portuguese labels *Objetivo*, *Contexto*, *Pedido*, *Restrições*, *Critérios de aceitação*, or their English equivalents). A deterministic guard refuses a reply that loses a dictated word or number, adds a number, adds a word that is neither dictated, from the pack nor a label, or uses pack words outside *Contexto*; a refusal, an Ollama failure or a reply slower than `[autorewrite] enrich_timeout_s` (15 s) types the corrected text. A dictation under 6 words is corrected but not enriched. In the Claude Code panel of VS Code the parts go on separate lines with Shift+Enter; in a terminal they are typed as one paragraph with their labels. One plain Enter follows the whole text. The indicator shows *A enriquecer o prompt para o Claude Code…* while the model enriches, then *Prompt enriquecido e enviado*, or *Enriquecimento recusado; foi o texto corrigido* (or the Ollama or timeout notice) when the corrected text was sent instead. Mouse 4, the middle click, `send_claude` and every other window keep the rewrite as before.
    - **Measured** on the Sponsor's real voice (`.venv\Scripts\python -m bench.prompts --require`, qwen3:8b in the shared Ollama, 15 recorded Claude Code prompts across 4 projects plus the 9 earlier claude-code dictation takes): domain-term errors with today's mouse 5 correction 7, new 5 of 16 term occurrences (7 already after the text pipeline; target at most half of today's, **not met**, a Sponsor decision in [docs/research/PROMPTS.md](docs/research/PROMPTS.md)); in all 24 takes, content words lost 0 and invented content words 0 with the new mouse 5 (targets 0, met), against 1 lost and 4 invented with today's correction (strict count; 2 of the 4 restored words that were said); pack words outside the context part 0; enriched prompts 3 of 13 asked on the prompts and 5 of 8 on the dictation takes (the others typed the corrected text); no call over the product timeouts. Latency p50/p95 on the prompts, with the shared GPU busy: transcription 0.42/0.47 s, today's correction 3.32/3.86 s, new correction 0.99/1.48 s, enrichment 3.27/7.91 s, new mouse 5 total after transcription 4.22/8.89 s (dictation takes 2.66/8.77 s; earlier runs of the same new mouse 5 gave 2.32/4.28 s and 3.79/8.15 s on the prompts).
  - **Middle click** (`[triggers.send_raw]`): the text as recognized and cleaned, never rewritten by the model, however long.

  In any other window (a file or the integrated terminal in VS Code, a browser, WhatsApp, ...) the text is typed without Enter and the indicator says *Não é o Claude Code: escrito sem Enter*. A rewrite followed by Enter is never offered to the undo key. The older `[triggers.send_claude]` (Enter in Claude Code, the rewrite only for a long dictation) still works for local files that use it; the example leaves it empty. An input bound in `local/quill.toml` is taken off the example's triggers, so an older local file that binds mouse 5 and the middle click to `send_claude` keeps loading. By default the `claude-code` profile is Windows Terminal with "Claude Code" in the title, or VS Code with the ` [Claude Code]` focused-view marker directly after the last "Visual Studio Code" of its title (a bracketed title entry matches only there or at the end of the title, so a file, folder or tab named `[Claude Code]` does not count). VS Code shows the marker only with this user setting, and only while the Claude Code view in the sidebar has the focus (set `"claudeCode.preferredLocation": "sidebar"` to open it there):

  ```json
  "window.title": "${dirty}${activeEditorShort}${separator}${rootName}${separator}${profileName}${separator}${appName} [${focusedView}]"
  ```

  **Claude Code editor tab and titles without the marker** (`[claude_code] focus_check`, on by default; `quill/uia.py`): for a VS Code window the title does not make `claude-code`, Quill asks Windows UI Automation, read-only and off the hook thread, which element has the keyboard focus. Only the message input of the Claude Code extension (identified in extension 2.1.287: an Edit element with the CSS-module class `messageInput_<hash>` inside `messageInputContainer_<hash>`, inside VS Code's webview frame; the same in the sidebar view and the editor tab) makes the window `claude-code`, with the project, context mode, enrichment and one Enter. A text editor, the integrated terminal, another webview (Markdown preview, settings), no answer within 0.8 s or no UI Automation at all keep the `vscode` profile: typed without Enter. The reader uses raw ctypes COM (no package), reads only the control type, class name and automation id of the focused element plus its ancestors' names (at most 64 parents), with UI Automation's connection and transaction timeouts, never reads a value or text, never sets the focus and calls no control pattern; only the verdict is logged (`focus check: claude_code_input`). It relies on VS Code exposing its accessibility tree, as it does with `"editor.accessibilitySupport": "on"` (the Sponsor's current setting); with it off, the editor tab is typed without Enter and the sidebar marker still works. Quill never edits VS Code settings. The pre-Enter re-check asks for the focus verdict again for a window recognised this way: the focus must still be in the Claude Code input. In the panel, Enter submits and Shift+Enter adds a line; Quill types line breaks as Shift+Enter and presses `[claude_code] send_key` once at the end: `"enter"` (default) or `"ctrl+enter"` when the extension's `claudeCode.useCtrlEnterToSend` is on. Claude Code in a terminal always gets Enter. Claude Code in the VS Code integrated terminal still cannot be told apart from a shell, so there the text is typed without Enter.

  Mouse 5 in the Claude Code extension (2026-10-02): the logged sessions got the `vscode` profile (no Enter, no enrichment) and `project: no_name`. Three title cases were examined; two are fixed now. (1) Fixed: the project hub title with no editor open (`<project> | - Visual Studio Code`) gave no project; it is now read. (2) Fixed, but not seen in the live titles: with `"editor.accessibilitySupport": "on"` and `accessibility.windowTitleOptimized` (on by default), the installed VS Code appends ` - <editor state>` (the active editor's decoration, such as *Modified* or its problems) after the marker, only when the active editor has such a decoration. Quill used to require the marker at the very end and the project title to end with "Visual Studio Code"; the marker and the project are now read before that optional suffix. None of the live VS Code titles checked had the suffix, so it is not shown to be the cause of the logged sessions. (3) Fixed by the focused-element check above: in the live windows the active editor was mostly a Claude Code conversation opened as an editor tab, whose title ends in an empty `[]` marker like other views, so the title alone cannot tell it apart. Just before the Enter of any send trigger, the target is described again: it must still be the foreground window of the same process, still `claude-code`, and its title must not have gained VS Code's dirty marker `●`; otherwise the text stays typed without Enter and the indicator says *O destino deixou de ser o Claude Code: escrito sem Enter* (logged as `enter_withheld` with a reason code).

  Check how a window is classified, read-only (no input, click, focus or window change; no title, project name or path is printed):

  ```
  py -3.12 -m quill.profiles --probe --delay 5
  py -3.12 -m quill.profiles --probe --all
  ```

  The first describes the foreground window 5 seconds later (bring the Claude Code input forward meanwhile); `--all` lists every visible VS Code and terminal window. Each line gives the process, the window class, the profile and the matcher that chose it, the focused-view marker kind (`claude-code`, `other`, `empty` or `none`), whether the editor state suffix is there, the focus verdict (`claude_code_input`, `text_editor`, `terminal`, `other`, `unavailable`, `timeout`, or `n/a` when not asked; asked for the foreground window only, never with names or text), the project-detection reason code and whether mouse 5 would press Enter. The Claude Code input of an editor tab shows `profile claude-code`, `rule claude-code (focus)`, `marker empty`, `focus claude_code_input` and `mouse 5 Enter yes` with `--delay 5`.
- **Command** (default: F14): select text, hold the key, speak an instruction (for example "põe isto mais formal", "traduz para inglês") and release. The selection is copied (the clipboard is put back), rewritten by the local Ollama model and typed over the selection. The trigger never clicks, so the selection is kept; terminals are refused, and on any failure the selection stays as it was and the indicator says why. Any free key can be added, for example F8 as well as F14 (F14 suits a Stream Deck style button):

  ```toml
  [triggers.command]
  keys = ["f14", "f8"]
  ```

  A key bound to a trigger loses its normal action in every program while Quill runs (F8 is, for example, "next problem" in VS Code), and an input can belong to one trigger only.
- **Voice commands** (default: F9; `[triggers.voice]`, at most one key and never a mouse button, `keys = []` turns them off): hold the key, say a command, release. The indicator shows *Comando de voz* with the live words. The trigger never clicks, types or presses Enter. Commands are a registry in `quill/voice.py` (a command recognizes the normalized text and runs; new commands are added without changing the parser); text that no command recognizes shows *Comando não reconhecido* and does nothing. The first command opens a project's Windows shortcut in VS Code. F9 is dedicated to voice commands, so no verb is needed: say the project name, alone or inside a phrase such as "abre VS Code no <projeto>" or "VS Code na pasta <projeto>". The verb and what Whisper hears for it, "VS Code" and its transcriptions, "projeto/pasta/repositório", prepositions and politeness words are ignored wherever they are; filler alone shows *Comando não reconhecido*. The name is searched anywhere in the utterance. When the name is not clear (no shortcut close enough, two names, or two shortcuts too close to each other) nothing opens and the indicator shows the closest names:
  - `quill/shortcuts.py` lists the `.lnk` files directly inside the folders of `[voice_commands] shortcut_dirs` (absolute paths, only in the ignored `local/quill.toml`; the example leaves it empty). The file name without `.lnk` is the project name. A missing or unreadable folder is logged by reason code and skipped.
  - F9 audio is always decoded in Portuguese, with its own Whisper prompt: a Portuguese command followed by the shortcut names and the personal-vocabulary names. The hotwords are only the personal-vocabulary names and their spoken variants (shortcut names listed a second time made Whisper repeat the list instead of hearing the name). Dictation keeps its own hints.
  - F9 audio is decoded by `[voice_commands] model` (default `large-v3`, local, already in `models/`); dictation keeps `[engine] model`. When the two differ, Quill loads the voice model after the engine model and keeps both loaded (about 3 GB more video memory). Until it is ready, or if it cannot load, F9 uses the engine model and the log says so. `--check` reports whether its files are present.
  - The spoken name, and the personal-vocabulary name it stands for (a name or one of its variants), is compared with the shortcut names ignoring case, accents, spaces and hyphens (a hyphenated name may be said as two words), by spelling and by a sound key (k/c/q, ph/f, y/i, silent h, doubled letters), within a small edit distance. An exact name beats a longer sibling ("alfa" opens alfa, "alfa public" opens alfa-public). A shortcut opens only when one candidate is inside the bound and clearly ahead of the next; the same name in two folders is one candidate only when both point to the same target. Otherwise nothing opens and the indicator shows up to 3 close names.
  - The target is read from the shortcut bytes, read-only, without launching it. A shortcut that starts VS Code is opened with the shell, as a double click would; a shortcut to a local folder starts VS Code on that folder with an argument list (never a shell string); any other target is refused. The indicator shows *A abrir <nome>*. Spoken text never reaches a shell, a command line or a file path, and logs carry reason codes, counts and timings only.

  Measured on 15 real recordings (`.venv\Scripts\python -m bench.voice_commands`, the app's voice model and hints): with large-v3, 15 of 15 correct and 0 wrong shortcuts (target at least 95 % and 0), release to final text p50 0.34 s, p95 0.38 s; with large-v3-turbo the same takes gave 12 of 15 (the 3 misses opened nothing). See [docs/research/VOICE-COMMANDS.md](docs/research/VOICE-COMMANDS.md).

  While Quill runs, F9 is swallowed and no longer reaches other programs (for example VS Code's breakpoint toggle); bind another key in `local/quill.toml` if you need it.
- A tap shorter than `min_hold_ms`, or another key pressed while a keyboard trigger is held (for example Right Ctrl+C), cancels: nothing is clicked or typed. While Quill runs, the bound mouse buttons and F keys do not do their normal action.
- A new press while the previous text is still being finalized starts recording at once; texts are typed strictly in order, each one once, into its own target. When a target closed, the foreground window changed, the microphone or the engine failed, or Ollama is down (the cleanup falls back to the rules), the indicator shows the error in European Portuguese and the next dictation is unaffected.
- **Automatic rewrite of long dictations** (`[autorewrite]`, on by default): a dictation over `min_audio_s` seconds of audio (15) or `min_words` words (40) is checked by the local Ollama model before it is typed, with a strict prompt that fixes misheard words from the context (window profile, the project in an editor's title, the personal vocabulary) and keeps every piece of information. A deterministic content guard refuses any reply that drops, adds or changes content. Short dictations never call the model (except from mouse button 5, above); the middle click never does. The indicator shows *A rever o texto* meanwhile; when Ollama is down, slower than `timeout_s` or the guard refuses, the original text is typed at once with a short notice. In the Claude Code panel of VS Code a rewrite may use several lines, typed with Shift+Enter (never Enter); in a terminal it stays one paragraph. A send trigger presses Enter once, after the whole text.
  - **Model warm-up** (`quill/ollama.py` `ModelWarmer`): the shared Ollama holds one model at a time and keeps it 5 minutes; loading qwen3:8b takes about 2 to 8 s, and a request that gives up aborts the load, so before this change a correction that met a cold model timed out at 4.0 s and left the next one cold too (measured: 48 of 48 corrections timed out). Quill now loads its own model in the background with an empty chat that generates nothing: when the speech model is ready (only with `[autorewrite] enabled`, and skipped while Ollama holds another project's model) and whenever a mouse 5 hold starts, so it loads while the Sponsor speaks; at most one warm-up is in flight, never on the hook thread, with a 60 s limit so the load is not aborted, and failures are only logged. A correction first waits at most `[autorewrite] load_wait_s` (8 s, 0 to 30) for the model to be in memory, then gives it `timeout_s`: it is corrected or typed as dictated within `load_wait_s + timeout_s` (12 s). After a timeout or failure the model is warmed again for the next dictation. `[autorewrite] keep_alive` (`"30m"`; `"1m"` to `"4h"`, `""` sends none) is sent only with Quill's own chat and warm-up requests; zero, negative, bare numbers and any unload value are refused by the config and by the client, and no request pulls, deletes or unloads a model. Measured with `.venv\Scripts\python -m bench.prompts --timeouts product` on both real sets, starting with no model in memory: before, 48 of 48 corrections timed out at 4.0 s; after, 0 timed out and 1 of 48 went over 4 s (the first, 8.4 s: 7.5 s of load, then 0.9 s), new correction p50/p95 0.67/0.92 s (prompts) and 0.89/1.04 s (dictation takes). See [docs/research/LATENCIA-CORRECAO.md](docs/research/LATENCIA-CORRECAO.md).
- **Undo key** (`[autorewrite] undo_key`, default F17; not a trigger key or the correction key): puts the original text back in place of the last automatic rewrite, within `undo_window_s` seconds (30), only in the same foreground window, before Enter, and while the manual-edit tracker proves the rewritten text is untouched with the caret at its end. It erases the rewrite with one Backspace per character as typed (a line break or an accented letter is one) and types the original, both as Quill's marked input; the correction key and edit learning then work on the original. Otherwise nothing changes and the indicator says why.
- **Claude Code alert** (`[claude_alert]`, on once its hooks are installed): when Claude Code, in the VS Code panel or a terminal, finishes its reply and waits for you, Quill plays a short Windows system sound and the indicator shows *Claude Code terminou*; when Claude Code asks for a permission it plays another sound and shows *Claude Code pede permissão*. Tool calls and intermediate text never ring. While a dictation or command is recording or being finalized, the alert waits until that session ends (kept once per kind, never lost or repeated) and a press stops a sound still playing, so the sound never reaches the microphone; alerts within 5 s ring once. Headless Claude Code runs (`claude -p`, the Agent SDK, a Claude Code started by another one) do not ring: the notifier reads `CLAUDE_CODE_SESSION_ATTENDED`, which Claude Code sets for every hook (`1` for a session someone uses, `0` otherwise); `filter = "unless-headless"` also rings for a Claude Code that does not set it, `"all"` rings for every session. The hooks are added only by this manual command, which prints the exact change to the user-level Claude Code settings and writes it only after you type `yes` (with a backup and an atomic write, keeping every other setting and hook; `--remove` deletes only Quill's entries):

  ```
  py -3.12 -m quill.claude_hooks --show
  py -3.12 -m quill.claude_hooks --install
  py -3.12 -m quill.claude_hooks --remove
  ```

  The installed hooks are `Stop` and `Notification` with the matcher `permission_prompt`, in exec form (no shell): the `.venv` `pythonw.exe` runs `quill\notify.py` by absolute path, with a 5 s timeout. The notifier keeps only the event name, `stop_hook_active`, `notification_type` and `cwd` from the hook input, never logs or stores the message or the reply, prints nothing, always exits 0 and sets a named Windows event in the user's session (`Local\Quill.ClaudeCode.Done` or `.Permission`): no network and no port. Before setting it, it writes the project name (the Git root folder name of `cwd`, else its folder name; never logged) to one small record in the ignored `local\alerts` folder, which Quill reads and deletes; without a record the alert shows without a name. When Quill is not running nothing happens. Hear the two sounds with `py -3.12 -m quill.sound --play-sound`.

  The indicator names the project with the alert (*<name>: Claude acabou*, *<name>: Claude pede permissão*; several projects waiting are all named, permission requests last). After the sound, a voice Windows already has says the project names (`speak_project = true`, the default): at most three, permission requests first, with hyphens, underscores and dots spoken as spaces, at `speech_volume` (0 to 100, default 80) and `speech_rate` (0.5 to 6.0, default 1.0, normal speed). It prefers the pt-PT voice of the Windows OneCore voices, then another Portuguese voice, then the default Windows voice; without any voice only the sound plays and the indicator still names the project. An alert within 5 s of the last sound speaks nothing, `sound = false` plays neither the sound nor the name, and `speak_project = false` plays the sound only. A dictation that starts cancels a pending name or ends the voice at once, before the microphone opens. The existing hooks need no reinstall (restart Quill). Hear one example with `py -3.12 -m quill.sound --play-sound --speak` (optionally `--project NAME`); check the voice without playing anything with `py -3.12 -m quill.speech --probe` (it prints only the voice language and the byte count).
- **Correcting**: select the corrected text of the last dictation and press the correction key (default F16), or just edit it by hand right after it was typed. A replacement seen in two dictations is applied automatically from then on. Review what was learned with `py -3.12 -m quill.review` (a reminder appears weekly in `--check`).
- **Indicator**: a non-activating, click-through overlay beside the pointer (or at the bottom center, `[indicator] position`), with the states *A carregar*, *A ouvir* with the live words and the voice level, *A transcrever*, *A rever o texto* (the automatic rewrite; *A enriquecer o prompt para o Claude Code…* while mouse 5 enriches), *Enviado para o Claude Code* (with *Prompt enriquecido e enviado* when the prompt was enriched), *Modo comando*, *Comando de voz* with the live words, *A abrir <nome>* (a voice command opened a project), the closest names or the reason when nothing was opened, *Claude Code terminou*, *Claude Code pede permissão* and *Erro* with its message. It never takes the focus.

Logs go to `local/logs/quill.log` (ignored, rotated at 1 MB): events, reason codes and timings per session, including the release-to-typed time, never spoken or typed text.

Sponsor-facing usage steps in European Portuguese: [docs/USAR.md](docs/USAR.md).

## The `quill` package

The dictation app lives in [quill/](quill/) (Python 3.12, standard library and ctypes Win32 only; the speech engine's packages are imported later, inside the `.venv`). `quill/app.py` wires the parts below (plus streaming recognition, cleanup, vocabulary, corrections, profiles and the indicator) and `quill/session.py` runs each push-to-talk hold as an ordered session; `quill/startup.py` manages the start-with-Windows entry. Among the parts:

- `quill/config.py`: settings. The committed [quill.example.toml](quill.example.toml) holds invented defaults; your own values go in `local/quill.toml` (ignored by Git), which is read over the example table by table. It sets the push-to-talk triggers (dictation, command, send to Claude Code with or without the rewrite, voice commands; mouse buttons `xbutton1`, `xbutton2`, `middle` and keys `f1` to `f24`, `right_ctrl` and a few others), `min_hold_ms`, click-to-focus, the microphone name, the indicator position, the active-window profiles, the local Ollama model, the cleanup mode and the shortcut folders of the voice commands. Unknown field names, a voice trigger with a mouse button or more than one key, a shortcut folder that is not an absolute path, an input bound to two triggers within one file, a non-loopback Ollama address and personal-data paths outside `local/` are rejected; errors name the field, never its value. Check a file with:

  ```
  py -3.12 -m quill.config --check local/quill.toml
  ```

- `quill/inject.py`: types text into the window captured when the trigger went down, as Unicode `SendInput` events tagged with Quill's marker. It never uses or writes the clipboard (a change made by another program while typing is reported), drops control characters, never produces a bare Enter from text (a line break becomes a space or Shift+Enter), waits for Ctrl/Alt/Windows to be released and checks before every burst that the target still exists, belongs to the same process, responds and is in the foreground. Elevated targets are refused. A plain Enter is only sent by the separate `press_enter(target)` call, used by the send-to-Claude-Code triggers.
- `quill/clipboard.py`: clipboard snapshots (all formats) with compare and restore.
- `quill/triggers.py`: the push-to-talk state machine (no Win32). A hold of a bound input emits `start` at once, `confirm` after `min_hold_ms`, then `stop` on release; a shorter hold, another key or button pressed while a keyboard trigger is held (a combo) or the hooks stopping emit `cancel`. Injected events (flagged by Windows or carrying Quill's marker), key auto-repeat, a release without a press and a second trigger while one is held are ignored. A missed release is recovered (live key state for inputs that pass through, a second press, or a 120 s maximum hold), so it never stays stuck. Bound mouse buttons and bound non-modifier keys such as F13 to F24 are swallowed while Quill runs (Back/Forward never fire); Right Ctrl, Right Shift and Right Alt pass through so shortcuts keep working.
- `quill/hooks.py`: the `WH_KEYBOARD_LL`/`WH_MOUSE_LL` callbacks only classify the event, queue it and return the suppression decision; a worker thread runs the state machine and the application's handler. Decisions and logs name the trigger input only, never other keys.
- `quill/focus.py`: click-to-focus. When a dictation or send-to-Claude hold (mouse 5, middle click or the older `send_claude`) is confirmed, it sends one primary-button click, marked as Quill's, at the current pointer position (it never moves the pointer), waits for the window under the pointer to take the foreground and captures it as the target. The command trigger never clicks, so the selection is kept. No click is sent when `click_to_focus` is off, over Quill's own windows, or while a modifier key or another mouse button is down (the middle button of a middle-click trigger does not count). A trigger on `right_ctrl`, `right_shift` or `right_alt` passes through to Windows, so it never clicks (a click would become a shortcut such as Ctrl+click): it types into the window that already has the focus.
- `quill/win32.py`: the ctypes layer. It has no call that moves the keyboard focus.
- `quill/sound.py`: the alert chimes (Windows system sounds through `winsound`, never waited for).
- `quill/speech.py`: the speaker of the project names. It starts the built-in Windows PowerShell 5.1 at its absolute `%SystemRoot%` path with `-NoProfile -NonInteractive` and no console window, running a constant script; the names, the rate and the volume reach it only on stdin as UTF-8 JSON (never in the command line) and are spoken as plain text through `Windows.Media.SpeechSynthesis`, falling back to `System.Speech`. Nothing is installed and nothing leaves the PC. The name starts no earlier than 0.8 s after the chime starts, and a starting hold cancels it or terminates the process without waiting. Errors are logged by exception type only.

Tests: `py -3.12 -m unittest discover -s quill/tests -t .`. They use a fake Win32 layer, a fake hook installer, a fake shortcut launcher and a fake speech engine and never create windows, install hooks, send input, open the microphone, play sound, start PowerShell, open shortcuts or programs or touch the real clipboard or the Claude Code settings; the real layer, the real hook installer, the real sound player, the real speaker (`quill.speech.PowerShellSpeech`), the real named events of the Claude Code alert, the real shortcut launcher and the default Claude Code settings path are disabled while they run.

### Manual typing self-test

```
py -3.12 -m quill.selftest.typing --allow-desktop-input [--targets edit,edge-textarea,edge-contenteditable,console,vscode]
```

It opens its own windows (a Win32 edit box, Edge app windows with a temporary profile, a console, VS Code with a temporary profile), takes the focus and types an invented corpus into each, then compares what arrived and checks that the clipboard is unchanged. Run it only when you choose, and do not touch the keyboard or mouse until it ends (about a minute). It writes an aggregate result, with counts of lost, extra and changed characters and never the typed text, to `local/selftest/typing-<UTC time>.json`. Without `--allow-desktop-input` it exits with code 2 and opens nothing. It is never part of automated tests or checks.

### Manual trigger self-test

```
py -3.12 -m quill.selftest.triggers --allow-desktop-input [--seconds 120] [--click-to-focus]
```

It installs the real hooks with the triggers from `local/quill.toml` (or the example) and prints every decision (action, trigger input name, signal and reason, for example `dictation xbutton1 cancel short_hold`) while you press, hold, tap and combine the triggers. While it runs the bound buttons and keys do not do their normal action. With `--click-to-focus` a confirmed dictation or send-to-Claude hold also clicks at the pointer, as the app does; nothing is typed. It ends after `--seconds` or with Ctrl+C and writes counts per action, reason and trigger input, plus per trigger input the press durations in buckets and how late the hook callbacks ran (never other keys, positions or window names), to `local/selftest/triggers-<UTC time>.json`. Without `--allow-desktop-input` it installs nothing: it validates the settings, lists the bound trigger inputs and exits with code 0 (2 when the settings are invalid). It is never part of automated tests or checks.

## Privacy

Audio, transcripts, personal vocabulary, learned corrections and API keys stay on the machine and are never committed. Audio only leaves the PC for the engine the user has explicitly chosen.
